Expense Policy Validator — Item Classification & Rule Engine

Build a system that reads itemized expense receipts, classifies every line item into a spend category, checks each receipt against written expense policies, raises evidence-grounded exceptions when a purchase is out of policy — and sketch, on paper, how you would run it on AWS.

Time ≈ 7 hours AI assistants expected AWS one-page design UI minimal viewer Model access OpenRouter key, any model Budget under $5

1 · Project goal

An audit team at Northwind Global receives thousands of itemized expense receipts. Most are routine. A few contain purchases that break company policy — alcohol on a solo meal, headphones booked as office supplies, a gift card, a spa charge claimed as lodging. Finding them by hand does not scale, and the keyword rules used before this caught the obvious cases while burying reviewers in false alarms.

Receipt→Normalise→Classify items→Find the rules→Apply the rules→Report exceptions

For each receipt your system produces: a category for every line item, the exceptions it raises (each naming the rule it breaks and the line items involved), any review signals, and a final disposition of flag, review, or pass.

How we work. Our team uses AI coding assistants (Claude Code, Cursor, Copilot and similar) every day, and we expect you to build this project the same way. Writing the code is not the test. We are looking at the decisions you make, how you check what the assistant produces, where you overrule it, and how honestly you report all of that.

This brief is deliberately detailed. It tells you what to build and what to measure, so you can spend your time building it well. If you fall behind, cut UI polish first and the evaluation last. A small, working, well-measured system beats a large unfinished one.

2 · What we provide

Policy documents — policy-docs/

Nine Markdown documents: meals and entertainment, technology and equipment, gifts and awards, non-reimbursable items, merchant category risk, receipt documentation, transaction patterns, regional rules, and approval and exception handling. Every rule has an identifier such as ALC-01 or TECH-02. The documents refer to each other, and regional-addendum.md overrides some global rules.

Receipts — receipts.jsonl

32 receipts and 79 line items, each with merchant, merchant category code (MCC), timestamp, currency and conversion rate, submitted expense type, attendee count, trip record, and pre-approval reference. Item descriptions appear in English, Spanish, French, German, Portuguese and Japanese. Every receipt comes with the correct answer:

FieldWhat it holds
line_items[].labels.categoryThe correct category for each item, plus a restricted true/false
labels.expected_exceptionsEach with rule_id, policy_doc, severity, the line_ids involved, and the reason
labels.review_signalsSofter signals that are not exceptions. Reporting one as a violation counts as a false positive.
labels.dispositionflag, review, or pass
notesWhy the correct answer is what it is, and the trap each receipt contains

Use the labels — including the notes field — only to evaluate your system, never as input to it or in a prompt.

Categories — category-taxonomy.md

21 categories, each marked restricted or not. Use this list as given — on this track, ignore the file's own invitation to add categories.

Data dictionary — README.md

Defines every field in the data, the conventions the correct answers follow, and how to compare your output with them. Read it before you start — it settles questions such as who an attendee count includes, and which field holds an approval reference.

What is in scope for this track

Every rule except the four transaction-pattern rules (TIME-01 to TIME-04 in transaction-pattern-rules.md) is in scope. Those four look at when a transaction happened, whether it belongs to a trip, and how receipts group together — a separate problem, so they are optional here.

That means four receipts are out of scope and will not be scored: RCP-020 and RCP-021 (a split transaction across two receipts), RCP-029 (an overnight purchase) and RCP-030 (a meal with no trip record). You will be evaluated on the other 28 receipts — 9 that should pass, 16 that should be flagged, and 3 that should go to review. Handling the four timing receipts is a welcome stretch goal.

Model access

We will send you an OpenRouter API key with your data. It is OpenAI-compatible: point your client at https://openrouter.ai/api/v1. Use it for generation and, if you like, embeddings. The choice of model is yours — any model OpenRouter offers, and local models are fine for any step. Never commit the key.

Model budget: under $5 in total — the key is capped there, the cap is firm, and we will not top it up. It covers only the model calls your validator makes through the key. Your own coding assistants run on your own accounts, are not counted against it, and should not be routed through this key.

Our recommendation, not a requirement: an efficient Haiku-class model is plenty for this task. Sending all nine policy documents and the taxonomy along with every receipt is about 190,000 input tokens — well under $1 on a model of that size, so $5 allows many full runs. Larger models cost several times more per run (check the price on OpenRouter's model page first), so the same $5 buys fewer runs. Say in your README which model you chose and why.

  • Cache. Classify each item once and save the result, so re-running your evaluation costs nothing. If the budget runs out, requests simply fail — the cache is your safety net.
  • Reproducibility. Set the temperature to 0 where you can, and record the model ID in each result file.
  • The data is synthetic. You may paste it into any assistant or model. Your README still says which services received it.
  • Spend is visible. We can see the key's usage on the OpenRouter dashboard; the Spend line in your README should roughly match it. The key is revoked after your review session.

3 · Part 1 — The pipeline Required · ~2.5 h

Build these five components, kept clearly separate in your code:

ComponentWhat it does
1. NormaliserCleans line-item text and translates non-English descriptions. How you translate is your call — an LLM step, a translation model, or a multilingual classifier.
2. Item classifierGives each line item a category from the taxonomy, a restricted flag, and a confidence between 0 and 1.
3. Policy retrieverFinds the rules that could apply to this receipt, using its items, its MCC, and its metadata.
4. Policy engineApplies the rules and decides. Covered in Part 2.
5. Exception reporterTurns the engine's output into findings a reviewer can read, each citing its rule and the policy text behind it.

Two things your classifier must get right — and that keyword matching gets wrong.

Names can mislead. "Beer-battered cod" is food. An "Arnold Palmer" is iced tea and lemonade. "Rum cake" is dessert. But "cooking wine" from a supermarket really is alcohol. Several receipts exist specifically to catch systems that match on words.

Context decides. The same bottle of wine is fine at a documented client dinner, a violation on a solo meal, and never allowed from a liquor store. The classifier only tells you what the item is — the rules and the receipt details tell you whether it is allowed.

Tip on retrieval: the policy corpus is small — nine short documents. A simple approach (keyword search, a small embedding index, or even passing the relevant documents straight to the model) is perfectly acceptable. Do not use a vector database.

4 · Part 2 — The policy engine Required · ~1.5 h

The policy engine must be plain, deterministic code — not an LLM call. The same receipt must always produce the same decision. It takes the classified items, the receipt details, and the retrieved rules, and decides. This is the part of the project you fully own, and we will ask you about it in detail.

It must handle:

  • Thresholds on USD amounts. Meal caps per person, alcohol caps per attendee, the $200 limit per equipment item, the $50 gift cap. Convert foreign currency first, using the rate on the receipt.
  • Carve-outs that need evidence. Some rules allow an exception only when something is recorded — a pre-approval, a baggage-delay reference, an attendee count. If it is missing, the carve-out does not apply.
  • Regional overrides. Where regional-addendum.md conflicts with a global rule, the regional rule wins.
  • Disposition. Rule EXC-01 in approval-and-exception-handling.md says exactly how exceptions turn into flag, review or pass. Implement it exactly — do not let a model decide it.
  • Low confidence. Rule EXC-03 says that when the classifier is unsure about an item, you raise a review signal instead of an exception. Pick a confidence threshold, and state the number you chose in your README. No correct answer uses EXC-03 — the answers assume every category is known — so each EXC-03 signal you raise counts as unmatched, as does any change it makes to a disposition. The data dictionary explains this.

Cover at least three of these cases, each of which has a matching receipt in the data:

5 · Part 3 — Evaluation Required · ~1.5 h

Report each of these on the 28 in-scope receipts:

  1. Classification. Both scored per line item, on the 65 items in the in-scope receipts: macro F1 across categories (the mean of the per-category F1 scores, over the categories that appear in the correct answers, counting a category you never predict as zero precision), and F1 on the restricted decision, with restricted = true as the positive class. Say what each score tells you about whether the policy engine is getting the inputs it needs.
  2. Disposition. A 3×3 confusion matrix of your flag / review / pass against the correct answers.
  3. False positives. Of the 9 receipts that should pass, how many did you flag or send to review?
  4. Missed violations. Of the 16 receipts that should be flagged, how many did you pass or downgrade to review?
  5. Keyword baseline. Build a simple keyword matcher over restricted words — the kind of system this project replaces — run it on the same receipts, and compare it with yours on the measures above. Say honestly where it does better, if it does.
  6. Two failure cases. Pick two receipts your system got wrong. For each, say which stage caused it — translation, classification, retrieval, or rule logic — and what you would change.
  7. The base-rate question. This dataset is unusual: more than half the receipts contain a violation, while a real expense stream has only a few percent. In three or four sentences, say what that does to the false-positive numbers you just reported, and what you would need to measure before trusting this system in production.

Optional stretch Precision and recall for each rule; for the exceptions that match an answer, how often they cite exactly the right line items; the four timing receipts.

6 · Part 4 — AWS deployment design, on paper Required · ~1 h

Write one page — a diagram is welcome but not required — describing how you would run your validator as a small, authenticated service on AWS. No code and no deployment; we will talk it through together in the review session. Cover these five things:

  1. Architecture. Which AWS services you would use for the API, the compute and the logs, and why. A small serverless design — for example API Gateway in front of Lambda — is a sensible starting point, but the choice is yours.
  2. The policy documents. Where they would live, and how an updated policy would reach the system.
  3. Authentication and secrets. How callers would authenticate, and where the OpenRouter key would be stored so it never appears in code.
  4. Cost. A rough monthly estimate at about 50,000 receipts a day, including the model calls. Show how you got the number.
  5. Before production. Two or three things you would add before real employees' receipts went through it — for example monitoring, handling a model outage, or protecting personal data.

7 · Part 5 — A simple viewer Required · ~0.5 h

Build a minimal Streamlit app (Gradio is fine too). You will use it to present your work. It needs three views:

  • Receipt list — every receipt with your disposition next to the correct one, mismatches easy to spot.
  • Receipt detail — each line item with its category and confidence, the exceptions raised with the policy text they cite, and the correct answer alongside.
  • Metrics — the numbers from Part 3 in one place.

Showing results you already computed is fine — no live model calls needed. Visual polish is not graded.
